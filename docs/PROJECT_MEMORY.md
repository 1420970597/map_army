# map.army 项目记忆

## 项目身份

本项目是对 `https://www.map.army` 免费托管版的长期、完整、可验证复刻。目标是让用户在相同操作条件下获得相同的交互语义、数据结果、导入导出行为和视觉反馈。实现可以采用不同技术，但不得因为实现成本、测试方便或“先做 MVP”而降低原站功能边界。

Pro 专属能力（账号、BFT、时间轴、私有 WMTS/WMS、密码保护分享等）不应伪装成免费版已支持；若决定实现，必须单独标注服务端依赖和验证范围。

## 永久工作规则

1. **完整迭代**：一个迭代的 ToDo 是交付契约。进入 PR 前，清单中的每一项都必须有代码、测试或可复现的验收证据；未完成项必须拆回后续 ToDo，不能用入口存在、部分可用或文档描述代替完成。
2. **先审计再编码**：先阅读官方索引 `https://www.map.army/doc/en/llms.txt`，再按功能页核对行为、输入边界、错误提示、数据格式、快捷键和视觉状态。只看源码入口不算功能完成。
3. **差异闭环**：每次 PR 创建、更新或合并后，都要重新检查原站与当前版本的差异，更新研究记录和 ToDo，并把新 ToDo 作为下一轮唯一范围。审计记录必须写明原站 URL、当前实现位置、差异、验收方法和是否属于 Pro。
4. **证据优先**：每项功能至少保留一种自动化测试、导入导出样例哈希、浏览器冒烟步骤或截图证据；涉及原站互操作时优先使用官方样例和真实格式往返测试。
5. **不降低语义**：状态机、撤销历史、锁定/隐藏、临时工具、单位/坐标系、权限/版本冲突和错误处理都属于功能本身。只实现主路径而遗漏边界语义，不得标记为完成。
6. **中文注释**：新增或修改的代码注释必须使用简体中文；用户可见文案按产品语言设置实现。提交信息使用 Conventional Commits，分支采用 `feature-*`、`fix-*`、`docs-*` 等可读命名。
7. **可部署交付**：每轮完成后运行 `npm run ci`，并执行 `docker compose up --build -d`、首页请求、`/api/health` 和 `docker compose ps` 验收。服务验证完成后保持本机环境可供用户检查，除非任务明确要求停止。
8. **PR 透明**：PR 描述围绕最终实现，列出原站依据、完成清单、未完成清单、测试命令、Compose 状态和提交 SHA。不得把旧路线图或历史声明当作当前事实。

## 标准迭代流程

### A. 建立审计基线

- 读取当前分支、最近 PR、工作树和现有 ToDo。
- 拉取或访问官方文档索引，按模块记录原站行为：地图/图层、符号与编辑器、坐标/网格、量测、导入导出、分享、选项、PWA、站点内容。
- 对每个差异标注优先级、影响、实现入口、测试证据和范围边界；同一行为只保留一个权威记录。
- 将本轮 ToDo 拆成可独立验收的条目，并明确完成判据。

### B. 实现与验证

- 先补纯逻辑测试和格式/互操作测试，再实现 UI 与服务端闭环。
- 每完成一个条目，立即执行对应测试和手动验收；跨模块改动要检查撤销、持久化、只读、锁定、隐藏、错误和刷新恢复。
- 对外部格式必须做“官方样例 → 导入 → 导出 → 再导入”往返，并记录丢失字段或兼容限制。
- 对交互功能要验证正常路径、取消路径、重复操作、边界输入、键盘/鼠标替代操作和移动端影响。

### C. PR 关闭门槛

只有以下条件全部满足，才可以把迭代提交 PR：

- 本轮 ToDo 每一项都标记完成，并有对应文件、测试或验收记录。
- `npm run ci` 全绿；必要时增加浏览器自动化或真实服务测试。
- Compose 镜像重建成功，前端、分享服务和健康检查均正常。
- 重新访问原站并完成差异复核；研究记录和下一轮 ToDo 已更新。
- PR 描述与实际代码一致，明确列出仍未完成的后续项目。

PR 合并后重复一次差异复核。若发现本轮条目并未达到完成判据，应立即开修复分支和修复 PR，不能把问题顺延成“已知限制”。
